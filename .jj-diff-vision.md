# The Vision: Next-Generation Diff Review for Jujutsu

## Executive Summary

Jujutsu's change-based model, automatic commits, and conflict-as-first-class philosophy represent a paradigm shift in VCS. However, diff tooling hasn't evolved to match. This document outlines three tiers of ambition for jj diff tooling: **Ideal** (think big), **Practical** (achievable), and **Good Enough** (MVP).

---

## Part 1: Understanding the Unique jj Diff Context

### What Makes jj Different for Diff Review?

1. **Change-Based vs Commit-Based**
   - Stable change IDs despite evolving commits
   - Need to diff between evolutions of the same change
   - interdiff is a first-class concept, not an afterthought

2. **Working Copy as a Commit (@)**
   - Every `jj st` is a new commit snapshot
   - Diffs should treat @ like any other revision
   - High-frequency state changes require performant tooling

3. **Conflicts as First-Class Citizens**
   - Conflicts live in commits, not just working copy
   - Can defer resolution indefinitely
   - Need excellent conflict visualization at any point in history

4. **The Squash Workflow**
   - `jj squash -i` is central to organizing changes
   - Interactive hunk selection is critical, not optional
   - Need fluid movement of changes between revisions

5. **Evolution Tracking (obslog)**
   - Changes evolve through rebases, squashes, descriptions
   - Want to compare "how did this change evolve?"
   - No existing tool visualizes evolution diffs well

6. **No Staging Area**
   - Use `jj new`, `jj split`, `jj squash` instead
   - Diff UX should embrace this, not fight it

## Part 2: Scenarios That Need Great Diff Support

### Scenario 1: Interactive Squash Workflow
**Context**: You have 5 files changed in @, want to split into 3 logical changes

**Current State**: `jj squash -i` opens terminal editor with basic diff
**Pain Points**:
- Text-based hunk selection is slow
- Can't see full context while selecting
- No preview of result before commit

**Ideal**: GitButler-style kanban lanes where you drag hunks between changes

### Scenario 2: Reviewing Evolution of a Change
**Context**: PR got feedback, you made changes, want to review what changed between v1 and v2

**Current State**: Manual `jj diff --from <old-commit> --to <new-commit>` with obslog archaeology
**Pain Points**:
- Hard to identify which commit in obslog to compare
- No visual timeline
- Can't see comments/descriptions alongside diffs

**Ideal**: Timeline view showing all evolutions with inline diffs between versions (GitHub-style PR review but for obslog)

### Scenario 3: Conflict Resolution Across Time
**Context**: A change has conflicts, you partially resolve them, come back later

**Current State**: `jj show` displays conflict markers
**Pain Points**:
- Hard to see which parts of conflicts are resolved vs not
- No visualization of 3-way merge context
- Can't diff "my resolution" vs "auto-merged base"

**Ideal**: P4Merge-style 4-pane view but integrated with jj's conflict model, with history of partial resolutions

### Scenario 4: Reviewing a Stack of Changes
**Context**: You have 10 stacked changes, want to review each individually and cumulatively

**Current State**: `jj log -p` or manual `jj show` on each revision
**Pain Points**:
- Hard to navigate between changes
- Can't see interdiffs between versions
- No "approve this change" workflow

**Ideal**: Stacked diff UI like Phabricator/ReviewStack with change tree navigation

### Scenario 5: Semantic/Structural Diffs
**Context**: Refactored code - renamed functions, moved blocks, reformatted

**Current State**: Line-based diff shows massive changes
**Pain Points**:
- Can't see "actual" semantic changes vs formatting
- Renames look like delete + add
- JSON/Markdown changes are noisy

**Ideal**:
- difftastic/mergiraf-style AST diffs for code
- mdslw preprocessing for markdown
- Image diffs for binary files (Beyond Compare-style)

### Scenario 6: Multi-File Review Context
**Context**: A change touches 15 files, reviewing them in sequence

**Current State**: Terminal pager or manual file-by-file
**Pain Points**:
- Lose context when switching files
- Can't mark files as "reviewed"
- Hard to jump between files

**Ideal**: VSCode-style multi-file diff with tree view, checkboxes, fuzzy search

## Part 3: The IDEAL Vision (Think Big)

### Core Philosophy
**"Diff review should be as fluid as your thoughts, as rich as your code, and as forgiving as jj itself"**

### Key Innovations

#### 1. **Change Canvas** (inspired by GitButler)
A spatial UI where:
- Each change is a vertical "lane" in a kanban-style board
- Drag hunks/files between lanes to reorganize
- See all changes simultaneously
- Real-time `jj squash` under the hood
- Works in terminal via tmux/multiplexing OR GUI

#### 2. **Evolution Timeline** (unique to jj)
- Horizontal timeline showing all evolutions of a change (from obslog)
- Click any point to see state at that time
- Swipe/arrow between evolutions to see interdiffs
- Annotations for "rebased", "squashed", "described"
- GitHub-style comment threads attached to specific evolutions

#### 3. **Intelligent Diff Engine**
Automatically choose the best diff strategy:
- **Code**: AST-based (mergiraf/difftastic)
- **Markdown**: Preprocessed with mdslw, word-level diffs
- **JSON**: Structural diff with jsonpatch visualization
- **Images**: Side-by-side with overlay/swipe (Beyond Compare)
- **Binary**: Hex diff with intelligent parsing (SQLite, PDFs, etc.)
- **Syntax highlighting**: git-delta level quality

#### 4. **Conflict Clarity**
- Visual 4-pane merge view (BASE | LOCAL | REMOTE | RESULT)
- Color-coded sections: "auto-merged", "resolved by me", "still conflicted"
- Save partial resolutions as you go (auto-commit in jj)
- History of conflict states in evolution timeline

#### 5. **Context-Aware Navigation**
- Fuzzy search across all files in diff
- "Next/previous change" that understands change boundaries
- Minimap showing where changes are in large files
- Breadcrumb trail of where you've reviewed

#### 6. **Rich Rendering**
- Inline images in markdown diffs
- Rendered HTML/PDF previews for docs
- Syntax-highlighted code in terminal (delta-level)
- Emoji/unicode support
- Hyperlinks to commits, issues, docs (delta --hyperlinks)

#### 7. **Workflow Integration**
- Mark files/hunks as "approved"
- Add inline comments (stored as jj describe annotations?)
- "Review mode" vs "edit mode"
- Integration with jj-stack for GitHub PR workflows
- CI status inline with diffs

#### 8. **Performance**
- Lazy loading for large diffs
- Incremental rendering
- Memoized diff computation
- Works smoothly with 1000+ file changes

## Part 4: The PRACTICAL Vision (Achievable in 6-12 months)

### Target: Neovim Plugin + Standalone TUI

#### Core Features

**1. Enhanced `jj squash -i` Replacement (Neovim)**
- Fork/extend hunk.nvim
- Add multi-target squashing (choose destination change per hunk)
- Better diff rendering with Treesitter syntax
- Keybindings for:
  - Move hunk to specific revision (fzf picker)
  - Split hunk into smaller pieces
  - Preview result before committing

**2. Change Tree Navigator (TUI)**
- Fork/extend jjui or lazyjj
- Add dedicated "review mode"
- Tree view of change graph on left, diff on right
- Keybindings:
  - j/k: navigate changes
  - d: show diff for current change
  - D: show interdiff with parent
  - e: show evolution timeline (obslog)
  - f: filter by file pattern

**3. Evolution Diff Viewer**
- New command: `jj evoldiff <change>`
- Shows side-by-side evolutions from obslog
- Interactive picker to select two evolutions to compare
- Integration with nvim for full editing

**4. Smart Diff Backend**
- Integrate difftastic as default for code
- Add mdslw preprocessing for markdown
- Configurable per file type
- Fallback to traditional diff

**5. Conflict Resolution UI**
- Better than current `:builtin` diff editor
- 2-pane view with conflict sections highlighted
- Easy navigation between conflict markers
- Integration with jj-diffconflicts

#### Implementation Strategy

**Phase 1: Neovim Plugin (3-4 months)**
- Create `jj.nvim` fork or contribute heavily to existing one
- Add Telescope pickers for changes, evolutions, conflicts
- Implement hunk.nvim-style squash UI
- Integrate difftastic/delta

**Phase 2: TUI Enhancement (2-3 months)**
- Contribute to jjui OR create new Rust TUI
- Add review mode with keyboard shortcuts
- Implement evolution diff viewer
- Add file tree navigation

**Phase 3: Polish & Integration (1-2 months)**
- Documentation
- Screencasts
- GitHub Actions for testing
- Integration with jj-stack

**Technologies**:
- Neovim: Lua + Telescope + Treesitter + plenary
- TUI: Rust + ratatui (like lazyjj)
- Diff engine: Call out to difftastic, delta, mdslw

## Part 5: The GOOD ENOUGH Vision (MVP in 2-3 months)

### Goal: Make the 80% use case 10x better

#### Minimum Viable Features

**1. Better `jj squash -i` (Neovim)**
- Single Lua plugin that enhances default diff-editor
- Syntax highlighting with Treesitter
- Easy hunk selection with visual mode
- That's it.

**2. Evolution Diff Helper (Shell Script + fzf)**
```bash
#!/bin/bash
# jj-evoldiff: Interactive evolution diff picker
jj obslog --no-graph -r $1 | fzf --preview "jj show {1}"
```
- Not pretty, but functional
- Can be improved later

**3. Better Diff Defaults (Config)**
```toml
[ui]
diff.tool = ["delta", "--side-by-side"]
diff.format = "git"  # Better than default

[merge-tools.difftastic]
program = "difftastic"
```
- Document best practices
- Provide example configs

**4. TUI Quick Win (Contribute to jjui)**
- Add "e" keybinding in log view to show evolution
- Add "E" to show interdiff with parent
- PR to upstream

#### Why This Is "Good Enough"

- Immediate value with minimal investment
- Uses existing tools (delta, difftastic, jjui)
- Can be done by one person in spare time
- Establishes patterns for "Practical" tier later

## Part 6: What Makes a jj Diff Tool Actually Better?

### Must-Have Differentiators

1. **Change-Aware**: Understands change IDs, not just commits
2. **Evolution-Native**: First-class support for obslog/interdiff
3. **Squash-Optimized**: Makes `jj squash -i` a joy, not a chore
4. **Conflict-Friendly**: Embraces jj's "conflicts in commits" model
5. **Performance**: Handles jj's high-frequency commit model

### Nice-to-Have Differentiators

1. **Semantic Diffs**: AST-aware for major languages
2. **Multi-Format**: Images, PDFs, JSON, etc.
3. **Review Workflow**: Mark files reviewed, add comments
4. **Stack Navigation**: Understand parent/child change relationships
5. **Visual Polish**: git-delta level syntax highlighting

## Part 7: Contribution vs Build New?

### Existing Tools to Extend

**Option A: Extend jjui**
- **Pros**: Active, Rust, good community
- **Cons**: May not have nvim integration goals
- **Verdict**: Best for TUI enhancements

**Option B: Extend hunk.nvim**
- **Pros**: Already jj-focused, nvim native
- **Cons**: Limited scope currently
- **Verdict**: Best for diff-editor improvements

**Option C: Extend jj.nvim**
- **Pros**: Aims to be "vim-fugitive for jj"
- **Cons**: Early stage, may not be maintained
- **Verdict**: Risky but high potential

### Case for Building New

**When to build new**:
- If you want evolution timeline UI (no existing tool has this)
- If you want change canvas/kanban interface (unique concept)
- If existing tools reject PRs for scope

**What to build**:
- Neovim plugin that composes existing tools (delta, difftastic, jj-diffconflicts)
- OR standalone TUI that focuses specifically on review workflow
- NOT a full Git client clone

## Part 8: Concrete Implementation Proposal

### Recommendation: **Hybrid Approach**

#### Path 1: "jj-review.nvim" (NEW)
A focused Neovim plugin for the review workflow:

**Features**:
- `:JJSquash` - Enhanced squash UI with hunk.nvim-style interface
- `:JJEvol` - Evolution timeline picker with interdiff
- `:JJReview` - Full-screen review mode with file tree + diff
- `:JJStack` - Navigate change graph visually

**Implementation**:
- Telescope for pickers
- DiffView.nvim integration when supported
- Call external tools: delta, difftastic
- ~1000 lines of Lua, max

#### Path 2: Contribute to jjui (EXTEND)
Add review mode features:

**Features**:
- New "Review Mode" tab (R key)
- Evolution diff view (E key)
- File tree with checkboxes
- Interdiff support

**Implementation**:
- Rust PRs to jjui
- ~500-1000 lines of Rust

#### Why Hybrid?
- Neovim users get deep editor integration
- TUI users get better jjui
- Shared concepts (evolution diff, review mode)
- Neither requires forking

## Part 9: Inspiration from Adjacent Spaces

### What We Can Learn

**From GitButler**:
- Virtual branches prove spatial UI can work for version control
- Drag-and-drop is powerful when it maps to underlying operations
- Real-time feedback (auto-commit) feels magical

**From Stacked Diffs (Phabricator, GraphiteHQ)**:
- Review granularity matters (per-change vs per-PR)
- Navigation between stack levels is critical
- Interdiff is essential for iterative review

**From difftastic/mergiraf**:
- Syntax-aware diffs reduce noise dramatically
- AST understanding enables better conflict resolution
- People want semantic diffs, not just line diffs

**From git-delta**:
- Beautiful output matters for daily use
- Hyperlinks to context are undervalued
- Word-level diffs are game-changing

**From mdslw**:
- Preprocessing hard-to-diff formats is viable
- One-sentence-per-line for prose is genius
- Tools can compose (mdslw + diff)

### Novel Ideas for jj

**1. Diff Preprocessing Pipeline**
```bash
jj diff --preprocess="mdslw:*.md,prettier:*.{js,ts},difftastic:*.rs"
```
- Per-format preprocessing
- Composable filters
- Config-driven

**2. Change Relationship Graph**
```
A
├── B (you are reviewing)
│   ├── C
│   └── D
└── E
```
- Show parent/child context in diff UI
- "This change builds on A, affects C and D"
- Visual change graph navigation

**3. Temporal Diff Scrubbing**
- Slider UI showing all evolutions
- Scrub through to see change develop
- Animated diff (see code transform over time)

**4. Conflict Heat Map**
- Visual indicator of "conflict density" across files
- Prioritize reviewing high-conflict areas
- Track resolution progress

**5. Review Checkpoints**
```bash
jj review-checkpoint -m "Looks good up to here"
```
- Mark progress in long review sessions
- Stored as metadata on changes
- Resume where you left off

## Conclusion

The gap isn't just "better diff viewing" - it's **enabling jj's full potential through tools that match its philosophy**.

Current diff tools are git-centric. They assume:
- Immutable commits
- Staging areas
- Conflicts are errors to fix ASAP
- Linear review workflows

jj diff tools should assume:
- Mutable changes with stable IDs
- Continuous working copy commits
- Conflicts are deferred collaborators
- Iterative, evolution-aware review

**The opportunity**: Be the first to build diff tooling that truly embraces change-based version control.

**The recommendation**: Start with "Good Enough" MVP (2-3 months), prove the concept, then expand to "Practical" tier with community support.

**The moonshot**: Eventually build "Ideal" tier as jj adoption grows and the ecosystem matures.
